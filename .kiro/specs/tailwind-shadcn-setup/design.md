# Design Document: Tailwind CSS v4 + shadcn/ui Integration

## Overview

This document describes the technical design for completing the Tailwind CSS v4 and shadcn/ui integration in the existing Astro blog project. The project already has the necessary packages installed (`tailwindcss`, `@tailwindcss/vite`, `@astrojs/react`, `react`) and the Vite plugin registered in `astro.config.mjs`. What remains is a small set of targeted file edits and one CLI invocation to wire everything together.

The integration is intentionally minimal: three file edits plus one CLI command. No new build tooling, no new frameworks, no architectural changes. The existing blog styles must be preserved throughout.

### Key Design Decisions

**Tailwind v4 import-based configuration**: Tailwind v4 uses `@import "tailwindcss"` in CSS rather than a `tailwind.config.js` file. The `@tailwindcss/vite` plugin handles scanning and CSS generation automatically. No config file is needed.

**CSS cascade ordering for style preservation**: Placing `@import "tailwindcss"` *before* the existing blog rules is the correct approach for Tailwind v4. Tailwind's preflight reset is injected at the `@layer base` level. The blog's explicit rules (which are not wrapped in any `@layer`) sit in the "unlayered" cascade, which has higher specificity than any `@layer` block. This means the blog styles naturally win without needing `!important` or explicit `@layer` wrappers.

**shadcn/ui with Tailwind v4**: The shadcn CLI's `init` command supports Tailwind v4 via the `--tailwind-version 4` flag. It injects CSS custom-property theme variables directly into the CSS entry point rather than generating a `tailwind.config.js`.

## Architecture

The integration touches four files and runs one CLI command. There are no new runtime dependencies beyond what the CLI installs (`clsx`, `tailwind-merge`, and Radix UI primitives per component).

```mermaid
graph TD
    A[astro.config.mjs<br/>@tailwindcss/vite plugin<br/>already registered] --> B[src/styles/global.css<br/>CSS entry point]
    B --> C[@import tailwindcss<br/>added as first line]
    B --> D[shadcn theme variables<br/>injected by CLI]
    B --> E[existing blog styles<br/>preserved below imports]

    F[tsconfig.json] --> G[baseUrl + @/* paths alias<br/>added to compilerOptions]

    H[src/lib/utils.ts<br/>cn utility] --> I[shadcn components<br/>src/components/ui/]

    J[npx shadcn@latest init] --> D
    J --> I
    J --> K[components.json<br/>project root]
```

### Data Flow

1. Astro's Vite build pipeline picks up `src/styles/global.css` via the layout's `<link>` import.
2. The `@tailwindcss/vite` plugin intercepts the `@import "tailwindcss"` directive and injects Tailwind's base, components, and utilities layers.
3. The blog's existing CSS rules follow the import and override Tailwind's preflight via cascade order.
4. shadcn/ui components import `cn` from `@/lib/utils` (resolved via the `@/*` path alias) and use Tailwind utility classes for styling.

## Components and Interfaces

### 1. CSS Entry Point (`src/styles/global.css`)

**Current state**: Contains Bear Blog CSS rules. No Tailwind import.

**After integration**:
```css
@import "tailwindcss";

/* shadcn/ui theme variables (injected by CLI) */
@layer base {
  :root {
    --background: ...;
    --foreground: ...;
    /* ... other shadcn variables ... */
  }
}

/*
  The CSS in this style tag is based off of Bear Blog's default CSS.
  ... (existing rules unchanged) ...
*/
:root {
  --accent: #2337ff;
  /* ... */
}
body { ... }
/* ... rest of existing styles ... */
```

The `@import "tailwindcss"` line must be the first non-comment line. The shadcn CLI will append its `@layer base` block after the import. The existing blog rules remain below both.

### 2. TypeScript Configuration (`tsconfig.json`)

**Current state**: `compilerOptions` has `strictNullChecks`, `jsx: react-jsx`, `jsxImportSource: react`.

**After integration** — adds two fields, leaves existing fields untouched:
```jsonc
{
  "compilerOptions": {
    "strictNullChecks": true,
    "jsx": "react-jsx",
    "jsxImportSource": "react",
    "baseUrl": ".",
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
```

### 3. `cn` Utility (`src/lib/utils.ts`)

A thin wrapper around `clsx` and `tailwind-merge`. All shadcn/ui components import this function to merge Tailwind class names correctly (resolving conflicts like `p-2 p-4` → `p-4`).

```typescript
import { clsx, type ClassValue } from "clsx";
import { twMerge } from "tailwind-merge";

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}
```

**Dependencies required**: `clsx` and `tailwind-merge` must be installed before the shadcn CLI `init` runs (the CLI will install them, or they can be pre-installed).

### 4. shadcn/ui Configuration (`components.json`)

Generated by `npx shadcn@latest init`. Records the project's shadcn/ui settings so subsequent `add` commands use the correct paths and style.

Key settings:
- `style`: `"default"`
- `tailwind.version`: `4`
- `tailwind.css`: `"src/styles/global.css"`
- `aliases.components`: `"@/components"`
- `aliases.utils`: `"@/lib/utils"`
- `tsx`: `true` (React JSX)

### 5. UI Component Directory (`src/components/ui/`)

Created by the shadcn CLI `init` command. Individual components (e.g., `button.tsx`) are added here by subsequent `npx shadcn@latest add <component>` commands. Each component file is self-contained and imports only from `@/lib/utils` and Radix UI.

## Data Models

This integration does not introduce new runtime data models. The relevant "data" is configuration:

### `components.json` Schema (relevant fields)

```typescript
interface ComponentsJson {
  $schema: string;
  style: "default" | "new-york";
  rsc: boolean;          // false — Astro is not Next.js RSC
  tsx: boolean;          // true
  tailwind: {
    version: "3" | "4";  // "4"
    config: string;      // "" for v4 (no config file)
    css: string;         // "src/styles/global.css"
    baseColor: string;   // "neutral"
    cssVariables: boolean; // true
  };
  aliases: {
    components: string;  // "@/components"
    utils: string;       // "@/lib/utils"
    ui: string;          // "@/components/ui"
    lib: string;         // "@/lib"
    hooks: string;       // "@/hooks"
  };
}
```

### CSS Custom Properties (shadcn theme)

The CLI injects CSS custom properties into `global.css` under `@layer base`. These use HSL channel values (not full `hsl()` declarations) to allow Tailwind's opacity modifier syntax:

```css
@layer base {
  :root {
    --background: 0 0% 100%;
    --foreground: 0 0% 3.9%;
    --primary: 0 0% 9%;
    --primary-foreground: 0 0% 98%;
    /* ... ~20 more variables ... */
  }
  .dark {
    --background: 0 0% 3.9%;
    /* ... dark mode overrides ... */
  }
}
```

These variables do not conflict with the blog's existing `--accent`, `--gray`, etc. custom properties because they use different names.

## Error Handling

### CSS Import Ordering Error

**Risk**: If `@import "tailwindcss"` is placed after any non-`@import` CSS rule, browsers and PostCSS will ignore it (CSS spec requires `@import` before other rules).

**Mitigation**: The implementation must insert the import as the very first line of `global.css`, before the existing comment block. The comment block itself is fine — CSS comments before `@import` are allowed.

**Detection**: If Tailwind utility classes don't generate styles in the browser, check that the import is the first non-comment line.

### Path Alias Resolution Failure

**Risk**: If `baseUrl` is missing from `tsconfig.json`, the `paths` alias won't resolve and TypeScript will error on `@/` imports.

**Mitigation**: Both `baseUrl: "."` and `paths` must be added together. Neither works without the other in TypeScript's module resolution.

**Detection**: `tsc --noEmit` will report `Cannot find module '@/lib/utils'` if the alias is misconfigured.

### shadcn CLI Init Failures

**Risk**: The CLI may fail if:
- `src/styles/global.css` doesn't contain `@import "tailwindcss"` (CLI checks for Tailwind setup)
- The `@/*` path alias is not configured (CLI validates aliases)
- `clsx` or `tailwind-merge` are not installable (network/registry issues)

**Mitigation**: Steps 1 and 2 (CSS import and tsconfig alias) must be completed *before* running the CLI. The CLI's error output is descriptive and will indicate which prerequisite is missing.

### Style Conflicts Between Tailwind Preflight and Blog CSS

**Risk**: Tailwind's preflight resets many default browser styles (margins, padding, font sizes on headings, etc.). If the blog styles don't override these, the blog's appearance will change.

**Mitigation**: The cascade ordering strategy handles this automatically. Tailwind preflight is in `@layer base`; the blog's rules are unlayered. Unlayered styles always win over layered styles at the same specificity. No `!important` or `@layer` wrappers are needed in the blog CSS.

**Verification**: After integration, visually inspect the Header, Footer, and a blog post page to confirm appearance is unchanged.

## Testing Strategy

> **Note on Property-Based Testing**: This feature is a configuration and setup task. All acceptance criteria involve file existence checks, CLI behavior, configuration file content, and CSS cascade ordering. None of these involve pure functions with varying inputs where 100 iterations would reveal more bugs than 2–3 iterations. Property-based testing is not applicable here. The Correctness Properties section is omitted accordingly.

### Smoke Tests (automated, fast)

These verify the static configuration is correct after the integration steps are applied.

| Test | What to check | How |
|------|--------------|-----|
| Tailwind import present | `global.css` first non-comment line is `@import "tailwindcss"` | Read file, assert line 1 (after stripping comments) matches |
| Import ordering | `@import "tailwindcss"` appears before any `:root {` or `body {` rule | Read file, compare line positions |
| tsconfig baseUrl | `tsconfig.json` `compilerOptions.baseUrl` equals `"."` | Parse JSON, assert field |
| tsconfig paths alias | `tsconfig.json` `compilerOptions.paths["@/*"]` equals `["./src/*"]` | Parse JSON, assert field |
| tsconfig existing fields preserved | `strictNullChecks`, `jsx`, `jsxImportSource` still present | Parse JSON, assert fields |
| components.json exists | File exists at project root | File system check |
| components.json tailwind version | `tailwind.version` is `"4"` | Parse JSON, assert field |
| components.json CSS path | `tailwind.css` is `"src/styles/global.css"` | Parse JSON, assert field |
| utils.ts exists | `src/lib/utils.ts` exists | File system check |
| utils.ts exports cn | File contains `export function cn` | Read file, assert content |
| ui directory exists | `src/components/ui/` directory exists | File system check |
| blog styles preserved | `--accent`, `body`, `main`, `.prose` rules still in `global.css` | Read file, assert substrings |
| shadcn theme variables | `--background`, `--foreground`, `--primary` in `global.css` | Read file, assert substrings |

### Integration Tests (manual or CI)

These require a running build or browser and verify end-to-end behavior.

| Test | What to check | How |
|------|--------------|-----|
| TypeScript compilation | `tsc --noEmit` exits with code 0 | Run command, check exit code |
| Astro build | `astro build` exits with code 0, no TS errors | Run command, check exit code and stderr |
| Tailwind class rendering | Add `class="text-red-500"` to a component, verify red text in browser | Manual or Playwright |
| Button component renders | Import `<Button>` in an Astro page with `client:load`, verify it renders with shadcn styles | Manual or Playwright |
| Blog visual regression | Header, Footer, blog post page look unchanged | Manual visual inspection |

### Test Execution Order

Integration steps must be completed before tests can pass:
1. Edit `global.css` → enables smoke tests 1–2 and integration test (Tailwind rendering)
2. Edit `tsconfig.json` → enables smoke tests 3–5 and integration test (TypeScript compilation)
3. Create `src/lib/utils.ts` → enables smoke tests 9–10
4. Run `npx shadcn@latest init` → enables smoke tests 6–8, 11–13 and integration tests (build, button)
5. Run `npx shadcn@latest add button` → enables button component integration test
